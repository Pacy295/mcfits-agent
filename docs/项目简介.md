# 项目简介

**麦门营养决策官（McFit Agent）** —— 用一句话说清预算和营养目标，系统在真实麦当劳菜单里给你几套"算得清、比得出"的配餐方案。

## 一句话定位

不是热量计算器，也不是点餐机器人，而是一个**在真实价格与官方营养之间做多目标权衡的决策助手**。

## 与普通麦当劳营养计算器的区别

| 普通营养计算器 | 麦门营养决策官 |
|---|---|
| 你选商品 → 它加总热量 | 你说需求（"40 元内，高蛋白，热量不超 750"）→ 它自己找组合 |
| 只回答"这个多少卡" | 同时回答"哪几套能同时满足预算、热量、蛋白质，各自贵在哪、强在哪" |
| 一个答案 | 2–4 套**具有不同搭配和取舍**的方案，并说明为什么保留多套 |
| 营养值抄表格 | 营养来自官方表逐项求和，价格来自 `calculate-price` 实时试算，带 `traceId` 与时间 |
| 不满足时无话可说 | 明确说"凑不出一餐"，并给出"放宽哪一项会怎样"的**已核价**结果与每项差距 |
| 改条件要重新自己算 | 改预算/蛋白/热量即时重算（重搜候选、重新核价、重判可行性与帕累托） |
| 套餐规格固定 | 可以直接把中杯可乐换大杯、中薯换大薯，营养与价格由服务端重新算 |

## 四个核心能力

1. **自然语言约束解析**
   区分硬约束与软偏好：「40 元以内」是硬上限，「高蛋白」只是倾向（不会偷偷变成 35g 下限），「最好来杯无糖可乐」是偏好，「必须有饮料」是硬约束。所有解析结果都能手动改。

2. **真实价格 + 官方营养的联合优化**
   候选必须来自当前门店真实在售商品，套餐组合必须通过 `rounds` 合法性校验；只有营养数据完整的组合才能参与求解；最终价格一律由 `calculate-price` 实算，未核价的方案不会出现在推荐里。

3. **多方案权衡，而不是单一最优**
   只在用户真正在意的维度上比较（价格永远在；蛋白只在你想要高蛋白时才作为"越高越好"；热量只有你明确想降才比低）。严格非支配的方案与"为丰富选择补充"的方案分开计算、分别标注。

4. **可验证的调整与诚实的边界**
   套餐内换规格 → 服务端重算营养、重新核价、重判约束；`unknown` 营养一律不按 0 处理；去酱/去冰这类没有营养数据的特制只展示、不算数；忌口类限制标注"无法验证"而不是假装满足。

## 技术组成（简述）

- 后端：Node.js 22，零 npm 依赖，内置 `fetch` 直连麦当劳 MCP（JSON-RPC over Streamable HTTP）
- 解析：规则解析 + LLM（OpenAI 兼容接口）双路，数值必须能在原话中找到，模型失败自动降级
- 优化：有限枚举 + 帕累托非支配 + 最远点差异化采样；候选规模与核价次数有上界并如实披露
- 前端：原生 JS/CSS，桌面与移动端两套布局
- 安全：只读工具白名单、服务端持有 Token/Key、按 IP 限流、输入长度上限、生产环境不读开发者本机配置

## 数据来源与边界

- 菜单、商品详情、套餐 `rounds`：麦当劳 MCP `query-meals` / `query-meal-detail`
- 营养：MCP `list-nutrition-foods`（160 条官方数据，未声明单位，按字段名与量级推断）
- 价格：MCP `calculate-price`（实时试算，不生成订单）
- **算不出来就说算不出来**：新品无营养数据、特制无营养变化、忌口无辣度/过敏原字段，这三类都明确标注，不用估算值填坑。

本项目为 WaytoAGI 1024 切磋大会用餐赛道参赛作品，与麦当劳官方无关，仅使用只读接口，不提供下单/支付/优惠券服务。
