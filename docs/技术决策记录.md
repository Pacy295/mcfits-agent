# 技术决策记录（第一阶段）

记录开发过程中的关键判断、被否掉的选项，以及支撑判断的实测证据。供后续阶段与比赛文档使用。

---

## 1. 独立应用如何真正调用 MCP

**结论**：绕过 WorkBuddy 的工具代理，由后端进程直接用 `fetch` 向 `https://mcp.mcd.cn` 发 JSON-RPC 2.0 请求。

**判断过程**

1. 先确认 MCP 是标准 Streamable HTTP 端点（`POST` + `Accept: application/json, text/event-stream`），返回体是 `data: {...}` 单事件 SSE 或纯 JSON。
2. 该端点**不要求**前置 `initialize` 握手，`tools/list` 与 `tools/call` 可直接调用（本地验证脚本先跑通，Node 侧复现成功）。
3. 因此**不存在**"WorkBuddy 能用、独立应用不能用"的问题 —— 前提是 Token 在服务端可用。

**实现要点**

- 只用三个 header：`Content-Type` / `Accept` / `Authorization`。**不要**加 `MCP-Protocol-Version`（实测非必需，加了徒增风险）。
- 响应解析策略：先判断是否含 `data:`，是则按 SSE 事件拆块取最后一个合法 JSON；否则直接 `JSON.parse`。
- 超时 20s + 指数退避重试 2 次（仅对网络错误与 429/5xx），令牌桶 8 req/s（官方限流 600/min，保守取 1/8）。

**证据**：`verify-stage1.js` A1/A2 —— 独立 Node 进程列出 35 个工具，读取服务端时间 `2026-10-24 14:12:31` + traceId。

## 2. Token 存放策略

**结论**：只存在于服务端进程内存，来源按 `环境变量 → 本地环境文件（不随仓库提供） → 本地开发者配置（不随仓库提供）` 优先级解析。

- 仓库内**零** Token：`.gitignore` 排除 `.env*`，代码只从上述来源读取。
- 所有对外响应只给 `{configured: boolean, source: 描述字符串}`。
- 日志/错误统一过 `redact()`，把 `Bearer xxx` 与 Token 字面量替换为 `***REDACTED***`。
- 验收项 F1 会扫描整份报告 JSON，确认无泄漏；另做过全仓库正则扫描，结果为 0 命中。

## 3. 营养匹配：宁可 unknown，不要近似

**结论**：五级匹配，只有前三级可自动采用，后两级一律 `unknown`。

| 级别 | 规则 | 采用 |
|---|---|---|
| L1 | 严格规范化后完全相等（全半角括号、空格、`™`、破折号、引号） | ✅ |
| L2 | 再去掉全部标点后相等（`麦辣鸡翅2块` vs `麦辣鸡翅-2块`） | ✅ |
| L3 | `data/nutrition-aliases.json` 中 `confirmed: true` 的人工别名 | ✅ |
| L4 | 包含关系候选 / 字面相似候选（bigram ≥ 0.5） | ❌ 仅作人工确认建议 |
| L5 | 无候选 | ❌ |

**为什么 L2 敢用**：只删除标点符号不可能改变规格或口味语义，属于字符层面的确定性归一。

**为什么 L3 必须人工确认**：`可乐`（无规格）→ 营养表有 `可乐小杯/中杯/大杯`；`那么大鸡排（椒盐风味）` → 营养表只有 `那么大鸡排`。这类"看起来像"的映射一旦自动采纳，就会把不同规格/口味的热量张冠李戴。因此：

- 已确认的 8 条别名都写了可复核的依据。例：
  - `可口可乐（中杯）` → `可乐中杯`：**同一份 MCP 数据的自证** —— code 3050 详情名是「可口可乐（中杯）」，而它在麦香鱼中套餐第 3 round 里的选项名是「可乐中杯」，与营养表条目完全同名；营养表另有无糖版本，说明「可乐X杯」即常规可口可乐。
  - `麦咖啡™冰美式中杯` → `冰美式中杯`：营养表 160 条咖啡全部无品牌前缀，菜单咖啡全部带「麦咖啡™」，属系统性命名差异。
  - `5块麦乐鸡` → `麦乐鸡5块`：仅词序差异，份数一致，门店无第二个 5 块装。
- 未确认的（`那么大鸡排（椒盐风味）`、`阳光橙麦炫酷`）保留在文件里作为候选，`confirmed: false`，不参与计算，并在覆盖率报告的"需人工确认"清单里列出。

**重复条目处理**：营养表内 `小杯玉米杯`、`纯牛奶（盒装）` 各出现两次，实测数值完全一致 → 取首条并在 `note` 里说明；若同名但数值不一致则降级为 `ambiguous`。

## 4. 套餐营养：组合求和，不走名称匹配

**结论**：`rounds.length > 0` 的商品一律不套用名称匹配，改为按组件求和，状态 `derived_sum`。

- 官方营养表**没有套餐级条目**（如「麦香鱼中套餐」），任何"直接查表"都是错的。
- 组件解析顺序：① 目录内商品自身详情名 → ② 现查 `query-meal-detail` → ③ 回退到 round 选项名。每条都记录 `resolvedBy`，便于审计。
- 求和口径明确写进返回值：`basis: '各组件官方标准值之和（官方未提供套餐级营养标示）'`。
- **任一组件 unknown → 整体 `partial`，`totals` 置 null**，只给 `knownSubtotal`。这是"不把不完整结果伪装成结论"的硬约束。

**顺带发现**：`可乐`（code 9900008751）其实是一个只有 1 个 round 的"选择饮料"容器（小/中/大杯、无糖版）。按组合求和处理，默认小杯 107 kcal —— 说明"是套餐"和"名字像单品"可以并存，不能按名字判断。

## 5. 缓存：分级 TTL，价格必须带时间戳

| 数据 | TTL | 理由 |
|---|---|---|
| 菜单 | 30 min | 门店菜单变了但详情缓存还在的概率低 |
| 商品详情（rounds/特制） | 12 h | 结构稳定；`?refresh=1` 可强刷 |
| 官方营养表 | 24 h | 官方静态表 |
| **价格** | **5 min** | 价格是会变的商业数据，长缓存等于造假 |

- 缓存键包含 `storeCode`：`detail:3350241:1600`，换门店不会串数据。
- 价格响应必带 `checkedAt`（本地核价时刻）与 `mcpDatetime`（MCP 返回时刻），并标记 `cacheMeta.cache = hit | miss | refresh-expired`。
- 核价失败时返回 `failed` + `stalePriceAvailable`，**不会**把旧价当现价返回。
- 另加 60s 的目录级去抖，避免每次请求都重建 117 个商品的对象图。

## 6. 只读白名单：从代码层禁止下单

**结论**：`McpClient.callTool` 第一步就检查白名单，非白名单工具直接抛 `blocked`。

- 白名单 24 个只读工具；`create-order` / `cancel-order` / `auto-bind-coupons` / `draw-lottery` / `mall-create-order` / `party-order-create` 等全部拦截。
- 这不是"靠自律"，而是硬编码在调用入口，任何上层代码都绕不过去。
- 验收项 A3 主动尝试 `create-order`，确认被拦截。

## 7. 特制（去酱/去冰）为何不做数值

前置验证已确认：`modification` 的 value 只有 `code/price/name/maxQuantity/minQuantity/selectedQuantity/selectedKey/unselectedKey` 八个字段，**无克数、无营养、无出液量**；`calculate-price` 也只回价格。

因此本阶段：

- 特制选项作为结构化数据完整保留（含 `selectedKey`，因为可乐四档冰量的 `code` 全是 `200002`，只能用 key 传参）。
- 营养侧统一返回 `modificationImpact: 'not_modeled'` 与一句明确说明。
- 不做"去酱 = 减 X kcal"的推算。唯一有内部数据支撑的差分（吉士 = 46 kcal）也只在文档里记录为**估算**，不进产品数值。

## 8. 开发中发现的真实数据事实（与前置验证报告的差异）

前置验证基于 63 个商品的样本，本次全量拉取后有几处变化，正好验证了"不能拿历史结果当现状"：

| 项目 | 前置验证（10-23 21:39） | 本次（10-24 14:12） |
|---|---|---|
| 门店商品数 | 63（6 个分类样本） | **117**（14 个分类全量） |

## 11. 用餐时段：只提示差异，不预测未来菜单

**背景**：用户早上 07:02 说「今晚…」，系统查的是当期早餐菜单并推荐麦满分，用户会误以为晚餐也能这样点。解析链路原本完全没有时段概念。

**决策**：
1. 识别用户明确说出的时段（今晚/明早/中午/早餐…），并与本次实际查询时段比对。
2. 不一致时只给一句提示：「现在只能核实当前（早餐）菜单，晚餐的菜单到点再查一次更准确。」不声称未来时段一定可售。
3. 不做未来菜单预测、预约、定时查询——未来菜单无法核实，按本项目一贯的「宁可 unknown 不要近似」处理。
4. 没提时段时 `mealTime=null`，推荐行为与之前完全一致。

**实现**：`src/parse/meal-time.js` 纯函数（`classifyPlannedPeriod` / `currentPeriod` / `analyzeMealTime`）；解析结果与 `/api/recommend` 透出 `mealTime`；前端在结果头部渲染一行提示（复用 `res-why` 样式）。

**边界**：时段判定基于服务端本机时钟；当前是单门店、单时区部署，若将来多时区部署，应改用 MCP `now-time-info` 的服务端时间。

**测试**：6 项离线用例（07:02 说今晚→提示；19:00 说今晚→不提示；明早→明天菜单现在无法核实；无时段→null；三种时段识别；解析结果附带 mealTime 且不改预算）。

**同期修正**：`npm test` 漏了 `test/stage5.test.js`（14 项），已补入脚本；stage3 的「规格替换」用例在命中价格缓存时 `checkedAt` 不再单调，改为强制重新核价后断言。

## 12. 推荐排序：目标优先，价格只做比较维度

**背景**：赛前实测发现，自动化测试全绿但推荐质量偏离用户目的——35–45 元预算给到 ¥21 套餐、高蛋白正餐首位是 ¥8.50 单份油条。

**根因（四条，全部是排序/候选问题，不是数据或模型问题）**：
1. 核价批次在"有预算上限"时按参考价升序取前 N 个 → 额度被最便宜的商品吃光，区间内/高蛋白候选根本没被核价，自然进不了结果。
2. 帕累托代表与价格梯度选择的首位固定取"最低价" → 价格抢位，主目标（蛋白）没有优先权。
3. 差异化补充为了凑数量，会把明显偏离主目标的便宜单品补进来（一份油条）。
4. 「无糖」完全没有进入解析：既没有偏好字段，也没有"含糖量不可核实"的提示。

**决策**：
- 核价顺序按用户目标排：有目标区间→区间内优先；要蛋白→蛋白高优先；预算只作后续收敛与兜底。
- 选择器首位由主目标决定（蛋白最大化时按蛋白），不再永远取最低价。
- 「一顿饭」语境（一顿/一餐/正餐/套餐）下，营养模式也排除单件方案；高蛋白场景低于最优蛋白 40% 的候选不能用来凑价位。
- 目标区间在日点评分中的权重由 +1.2 提到 +2.5（高于一份小食的分值），但低于下限仍不扣分、不怂恿加餐。
- 无糖按名称证据判断（无糖/零糖/零度/0 糖）；没有证据时明确写「含糖量未核实」，不冒充。
- 放宽约束的结论必须有真实重搜支撑：已核价集合里放宽后仍为 0 时，按放宽条件重新取候选并真实核价（每约束最多 5 个、总共 12 个），并说明"仅限本次搜索范围"。
- 方案数量不强制凑满：只有一两套有意义就给一两套。

**验证**：完整回归 100/100；新增 `test/recommend-quality.test.js` 5 项（单件油条不得入选、区间参与排序、无糖按名称证据、无糖不得冒充、数量不凑满）；三个原始输入真实 MCP 复跑见 `docs/赛前推荐质量修复报告.md`。
