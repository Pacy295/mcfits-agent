## 五、用餐时段语义检查（问题存在，已最小修复）

**实测确认问题存在**：07:02 输入「今晚…」，解析结果里没有任何时段字段，系统直接用当期**早餐菜单**推荐麦满分，且页面无任何提示——用户会误以为晚餐也可这样点。

**修复（最小范围）**：

- 新增 `src/parse/meal-time.js`：识别「今晚 / 明早 / 中午 / 早餐 / 夜宵」等明确时段，与本次实际查询时段比对；
- 不一致时只给一句提示，不声称未来可售、不预测未来菜单、不做预约/定时查询；
- 解析结果与 `/api/recommend` 透出 `mealTime`；前端在结果头部渲染一行提示；
- 未提时段 → `mealTime=null`，推荐行为完全不变。

**实测验证**：

| 场景 | 结果 |
|---|---|
| 07:37 `/api/parse`「今晚…」 | `planned=dinner, current=breakfast, mismatch=true`，提示「你说的是晚餐，现在是早餐时段；现在只能核实当前菜单，晚餐的菜单到点再查一次更准确。」；预算仍为 35–45，warnings 仍为空 |
| 07:37 `/api/recommend`「今晚…」 | 200，3 套方案，带同一条时段提示，最高价 ¥18.00（≤45） |
| 07:38 `/api/recommend`「40元以内尽量高蛋白」 | 200，4 套方案，`mealTime=null`（无时段不打扰） |
| 离线单测（6 项） | 07:02 今晚→提示；19:00 今晚→不提示；明早→明天的菜单现在无法核实；无时段→null；三种时段识别；解析附带 mealTime 且不改预算——全部通过 |

**边界**：时段判定用服务端本机时钟（当前单门店单时区）；若将来多时区部署，应改用 MCP `now-time-info`。
