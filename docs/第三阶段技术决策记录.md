# 技术决策记录（第三阶段）

把「技术验证台」升级为「普通用户能直接用的产品」。前两阶段的决策见 `技术决策记录.md`、`第二阶段技术决策记录.md`。

## 1. A1：不可行解释只针对"用户真正启用的约束"

**现象**：真实验收输入只有 `budgetMax=12 / proteinMin=45 / requiredCategories=["drink"]`，但报告里出现了「去掉热量上限」。

**根因（两层）**：

1. 验收脚本用 `{ ...constraintsB, budgetMax: 12, ... }` 构造输入，把上一用例 B 的 `caloriesMax: 750` 顺手带了进来 —— **输入和说明不一致**，这是上一轮已经出现过一次同类问题的复发。
2. `analyzeInfeasible` 虽然会跳过 `null`，但没有"启用集合"的显式概念，也无法对外证明自己没越界。

**修复**：

- 引擎侧先算 `enabledKeys`（`budgetMax / caloriesMax / caloriesMin / proteinMin / requiredCategories` 中真正有值的），放宽分析只遍历这个集合；返回值新增 `enabledConstraints` 与 `relaxedConstraints`，让界面和测试都能核对。
- 验收脚本改为**逐字段显式构造**输入（不再 spread），并把真实入参打印进报告。
- 新增验收项 E6：`relaxedConstraints ⊆ enabledConstraints`，且不得出现 `caloriesMax`。
- UI 端在不可行面板顶部直接列出"你启用的硬约束"。

## 2. A2：不宣称"全麦当劳最优"

**问题**：引擎曾把方案标成「综合最优候选」，这在只核价了 40 个候选的情况下没有依据。

**修复**：

- 引擎的 `label` 改为中性的「方案 N」，另给机器可读的 `pickReason`；**面向用户的标签由前端依据真实数值生成**：
  - 最低价 → 「当前已核价候选中最省钱」；同价并列 → 「同样最低价 · 不同搭配」
  - 有高蛋白倾向且蛋白最高 → 「高蛋白选择」
  - 其余 → 「换一种搭配 / 更接近你的偏好」
- 这些标签只在满足条件时出现，不固定贴在任何一张卡上。
- 帕累托口径（是否非支配、被谁支配、差价多少）放在「为什么推荐 · 数据来源」的折叠面板里，与 traceId、核价时间并列。
- 页面顶部始终显示 `searchScope`：「候选 2066 个，核价 40 个，覆盖部分候选（非穷举）」——**先把搜索范围说清楚，再谈推荐**。

## 3. B：交互式决策空间

**做法**：约束面板是"可开关的条件"，不是"只读回显"。

- 四个数值条件各有开关：关闭即 `null`，并清空输入框（避免灰色框残留一个看起来生效的数字）。
- 必含类别、优化倾向、偏好词、排除词都是可编辑 chips。
- 任何改动 → 420ms 防抖 → **重新调用 `/api/recommend`**（重新生成候选、重新核价、重新判定可行性与帕累托），不是在前端过滤旧结果。
- 并发与顺序：
  - `state.seq` 自增，响应回来时若 `seq !== state.seq` 直接丢弃；
  - 同时 `AbortController` 取消上一个在途请求；
  - 校验用例：连续把预算改成 30/55/45，最终展示必须是 45 的结果（实测通过）。
- 状态反馈：骨架屏（计算中）、错误卡片（带重试）、不可行面板（放宽建议 + 近似方案）、模型降级横幅（说明已改用规则解析）。

**为什么不做前端本地过滤**：预算/蛋白一变，可行集合与最优结构都会变（比如预算收紧后原本靠后的便宜套餐才进入前沿）。本地过滤旧结果会给出"看起来可行但其实没重新核过价"的方案。

## 4. C：套餐真实规格替换（本阶段核心）

**接口**：`POST /api/plan/rebuild`

```jsonc
// 套餐
{ "productCode": "9900005460", "choices": [{ "round": "3", "code": "3100" }], "constraints": {...} }
// 单品组合
{ "components": [{ "code": "1600", "quantity": 1 }], "constraints": {...} }
```

**服务端处理顺序**（前端不许自己改营养或价格）：

1. 读 `query-meal-detail` 的 rounds，校验：round 存在、不重复、数量完整、选项属于该 round（否则 `illegal_choice` 并回传该轮合法选项）。
2. 用所选组件重新 `composeNutrition`（官方营养逐项求和；缺数据 → `partial`）。
3. `calculate-price` 实算（rounds 组合），返回金额、核价时间、traceId。
4. 用 `violates()` 逐项复核当前约束，返回 `satisfied[]` 与 `violations[]`（含 `excessFen` / `shortfall`）。
5. 组装成与推荐方案同构的 plan（`buildPlan` 复用），前端只负责渲染。

**选项级营养标注**：`GET /api/products/:code/rounds` 现在会为每个选项带上 `nutrition.status`。没有官方数据的选项在下拉里显示「（该选项无官方营养数据）」，该轮还会提示「N 项无营养数据」。实测麦香鱼中套餐的饮料轮 20 个选项中有 3 个（多汁柠柠、热美式中杯、热奶铁中杯）无法匹配。

**特制（去酱/去冰/去吉士）**：只在详情面板里**展示**，明确写"官方没有这些特制后的营养数据，系统无法计算，也不会把特制版本当成满足营养条件"。不提供开关，避免用户以为自己拿到了特制后的热量。

**实测**（麦香鱼中套餐，真实 MCP）：
- 默认：¥34.00 / 761 kcal / 20 g 蛋白
- 可乐中杯→大杯：¥36.00 / 838 kcal（+77）/ 蛋白不变
- 中薯条→大薯条：¥36.00 / 851 kcal（+90）/ 蛋白 +2

## 5. D：正式产品 UI

**页面结构**（单页，四区）：

1. **Hero**：一句话说明产品在做什么 + 大输入框 + 4 个示例短语 + 解析状态条。
2. **条件面板**：预算/热量上下限/蛋白下限（可开关）+ 必含类别（硬）+ 优化倾向（软）+ 想吃/不要 chips + 无法验证的忌口提示 + 待确认问题。
3. **推荐区**：2–4 张方案卡，含真实商品名、组成、MCP 实算价与核价时间、四项营养、满足条件数、帕累托标识、可展开的"为什么推荐"；底部固定对比条。
4. **详情抽屉**：规格下拉（rounds）、价格与 traceId、六项营养（热量/蛋白/脂肪/碳水/钠/钙）、逐条条件核对、特制说明。

**关键取舍**：

- **不使用商品图片**。MCP 详情里有 `image` 字段，但直接用存在素材授权问题，且"按名字配图"极易错配。当前版本纯文字 + 排版承担信息层级。
- **不迁移 React**：后端 API 已固化（状态枚举 + 来源字段 + 错误码），原生 JS 足够撑住当前交互复杂度；引入构建链的收益不抵成本。
- 移动端：条件面板 2 列 → 1 列，卡片单列，详情变底部抽屉（92vh），顶栏不换行、品牌名不截断。
- 明确免责声明（页脚 + 顶部工程台入口分开）：与麦当劳官方无关、只读接口、不下单。

## 6. F：模型配置与运行安全

| 事项 | 做法 |
|---|---|
| 本机模型 vs 部署模型 | `MCFIT_LLM_ALLOW_LOCAL`（默认跟随 `NODE_ENV`）：生产环境**不读取** `本地开发者配置（不随仓库提供）`，必须显式配置 `MCFIT_LLM_BASE_URL/API_KEY` |
| 额度归属 | `/api/llm/status` 返回 `sourceKind`（`developer-local` / `deployment-env`）与 `quotaNote`；点击顶栏模型徽章会弹出说明 |
| 密钥保护 | 只在服务端内存；前端只拿到模型名与来源；验收项 14 扫描页面源码与响应 |
| 滥用防护 | `parse 20/min`、`recommend 30/min`、`rebuild 60/min`（按 IP+路由），超限返回 429 + `Retry-After` |
| 输入限制 | 需求文本上限 500 字符（可配），超长返回 `input_too_long` |
| 错误处理 | 模型失败 → 降级规则解析并明确标注；MCP 失败 → `price_failed`，不回填旧价 |

本轮**没有**发布公开服务、没有改动已有模型配置。

## 8. 仍存在的限制

1. **新品无营养数据**：117 个在售商品里 40 个（龙焰系列、枫糖厚松饼系列、心形薯饼等）缺官方营养，不能进入严格求解；套餐里含这些组件的也会被标为营养不完整。
2. **搜索非穷举**：核价上限 40 个候选，`completeness` 标注为 partial；因此标签只说"当前已核价候选中…"。
3. **特制营养不可算**：去酱/去冰只展示不算。
4. **忌口无法验证**：无辣度/过敏原字段。
5. **单品组合方案不支持换项**：详情抽屉对 `kind=single` 只展示组成（换项需要重新生成推荐）。rounds 替换是本轮 P0，任意加减配料未做。
6. **限流是单进程内存**：多实例部署需要换成共享存储。
