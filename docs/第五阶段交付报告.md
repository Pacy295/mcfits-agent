## 1. 修改前后的架构和交互区别

### 交互流程

| | 修改前 | 修改后 |
|---|---|---|
| 首页主体 | 复杂条件面板（预算/热量/蛋白上下限等专业字段，问题现场一句话被展示成 10 个字段） | 「今天想吃点什么？」大输入框 + 示例短句 + 一个按钮 |
| 输入之后 | 解析完还要再点一次「重新配餐」 | 解析完成**自动搜索**，直接给出推荐 |
| 需求展示 | 原始字段表单 | 人话标签（如「¥60 左右的套餐」「偏清淡」「不太吃辣」「不喝冰饮」「想吃温和点」），旁边有「调整条件」入口展开完整编辑器 |
| 结果展示 | 全量候选 + 帕累托术语 + traceId + 搜索量 | 主推 1 套 + 备选 1–2 套（「不合口味可以换这几套」），技术信息全部折叠进详情/工程台 |
| 推荐排序（日常） | 默认最便宜优先 | 硬约束 → 口味偏好 → 合理搭配 → 预算意图 → 多样性（`selectDailyPlans`） |
| 预算语义 | 数字一律当上限 | `budgetIntent` 五分类：max / target / target_with_cap / minimize / unspecified（「推荐一个 60 元的套餐」≠「不超过 60」） |
| 偏好语义 | 忌口与口味混在硬排除 | 三级分离：真实忌口（hard，进排除）／口味偏好（soft，尽力满足）／用餐背景（肚子不舒服只做背景，**不做医学判断**） |
| 无法验证的偏好 | 大黄色警告框堆叠 | 尽力满足 + 卡片内 11px 小字诚实提示（实测黄框 0 个） |
| 反问 | 较频繁 | 全流程最多 1 个关键确认，且仅热量矛盾/过敏类（场景 B 零反问） |
| 等待体验 | 解析 ~16–21.5s 无反馈感 | 简短加载状态；同一句话重复提问**秒回**（解析缓存） |

### 架构层面

- 新增**意图层**（`src/parse/intent.js`）：`resolveIntent` → `intentChips` → `singleClarification`，预算意图用纯原文正则证据（`intentSource: raw-regex/fallback/hint`），不做无据推断。
- 新增**日常决策层**（`src/optimize/daily.js`）：确定性打分（组合完整性 → 辣味淘汰 → 饮品温度 → 脂肪辅助 → 口味匹配 → 价位意图），不依赖 LLM 主观评分。
- 优化器（`engine.js`）按 `mode: daily | nutrition` 分流：日常走 daily 排序；明确营养目标仍走原帕累托/多目标路径（14 项成熟能力全保留）。
- P2 响应优化：解析缓存（LRU+TTL）+ 并发去重 + LLM 超时 40s→20s。

## 4. 场景 B 实际推荐详例（本轮最重要真实用户测试）

原话：「最近肚子有点不舒服，不是很喜欢吃油的，也不喜欢吃辣的吃冰的，你给我推荐一个60元的套餐。」

**解析**：`source=llm`（mimo-v2.6-pro，8967ms，本次调用）→ `budgetIntent=target_with_cap(60)`，标签：「¥60 左右的套餐」「偏清淡」「不太吃辣」「不喝冰饮」「想吃温和点」，**0 反问**。

**主推：板烧鸡腿堡四件套 ¥57.50**（已按官方接口核价）
- 组成：板烧鸡腿堡 + 中薯条 + 麦乐鸡 4 块 + 可乐中杯（主食 + 小食 + 饮料，一顿完整正餐；不是最低价单品汉堡）
- 核价：`calculate-price` 实算，`status=valued`，`mcpDatetime=2026-10-24 21:21:37`，`traceId=2b5d9c4c47c9cc83bbfb0c05ade4723a`，估算 ¥57.50 与实价一致（`estimateMatched=true`）
- 营养（官方值求和）：997 kcal / 蛋白 39g / 脂肪 39g / 碳水 120g
- 适合理由：①一顿完整的饭 ②脂肪 39g，用来辅助避开高油搭配 ③¥57.50，接近你要的价位

**备选 1：板烧鸡腿堡套餐（低脂取舍）¥39.00**——脂肪仅 18g（更符合「不吃油」），价位稍远；**备选 2：不素之霸双层牛堡四件套 ¥59.50**——最贴 60 元价位。均经 MCP 实核价（traceId 齐全）。

**偏好处理结果**：
- 「不喜欢吃辣」→ soft 软偏好，不进硬排除；主推按名称避开明显辣味
- 「不吃冰的」→ 不含明确冰品
- 「不吃油的」→ 用官方脂肪数据辅助排序（39g < 48g < 49g 有序）
- 「肚子不舒服」→ 只做背景，不做医学判断

**未知限制（小字提示，非警告框）**：
- 「按名称避开明显辣味，辣度本身没有官方数据」
- 「可乐中杯的温度待核实」
- 「『清淡』只用脂肪数据辅助排序，不代表医学或官方认定」
- 「『肚子不舒服』只是背景，是否适合你需要你自己判断，系统不做医学建议」

界面实测（E2E step 15）：需求标签 5 个、主推 1 / 备选 2、提示字号 11px、黄色警告框 0、反问 0。

## 8. 解析和推荐实际耗时变化

同一工具 `scripts/perf-parse.mjs`（7 组输入 × 2 轮，真实 HTTP 调用，实测统计）：

| 指标 | 优化前（基线） | 优化后 | 变化 |
|---|---|---|---|
| 冷启动 解析 | min 5835 / 中位 7869 / max 14752 ms | min 3241 / 中位 7867 / max 14653 ms | 基本持平（由模型推理主导） |
| 冷启动 推荐 | min 250 / 中位 481 / max 2771 ms | min 483 / 中位 1589 / max 4925 ms | 同量级波动 |
| 冷启动 总等待 | min 6285 / 中位 8534 / max 17523 ms | min 4801 / 中位 8663 / max 19578 ms | 同量级 |
| **重复 请求 解析** | min 4705 / 中位 6773 / **max 43616 ms** | **min 3 / 中位 3 / max 8 ms** | **约 1000 倍**（缓存 7/7 命中） |
| 重复 请求 推荐 | min 235 / 中位 2069 / max 10505 ms | min 199 / 中位 1000 / max 2352 ms | 尾延迟消除 |
| **重复 请求 总等待** | max **54121 ms**（超时降级个案） | max **2360 ms** | 尾延迟消除 |

**优化手段（只做真实提速，无假进度、无预写结果）**：
1. **解析缓存**：LRU 200 条 + TTL 10 分钟，只缓存成功 LLM 结果（降级结果不缓存）；`MCFIT_LLM_DISABLE=1` 时读写全绕过（保住「模型不可用→降级」验证语义，parse.test.js 场景 J 依赖此边界）；同句并发请求合并为一次模型调用。
2. **尾延迟收紧**：LLM 超时 40s → 20s（`MCFIT_LLM_TIMEOUT_MS` 可调），超时即诚实降级规则解析。最坏等待从 43.6s+ 降到 ~20s。
3. **评估后放弃提示词瘦身**：实测冷解析由模型推理/生成主导（usage 显示 reasoning tokens 占大头），提示词预处理占比小，瘦身收益有限且有语义回归风险，如实说明不做。

历史参照：第五阶段初期场景 B 解析曾达 21.5s（llm 21560ms）；本次实测场景 B 冷解析 6.1–11.6s（模型随负载波动），同一句话再问即 3–8ms。

## 9. 未解决的问题及其影响

1. **冷启动解析仍需 3–15s+**（模型推理主导，不承诺固定秒数）。qwen3.8-flash 端点 403 未购，无法多端点竞速；仅 mimo-v2.6-pro 可用。影响：用户第一次提问有可感知等待（界面有简短加载态）；重复提问已秒回。
2. **约一成首次解析可能超过 20s 而降级规则**（本次六场景实测中场景 A 即触发一次；降级后推荐仍正确、标签略少，且界面如实标注）。如需提高首次命中可调大 `MCFIT_LLM_TIMEOUT_MS`，代价是最坏等待变长。属于「快而诚实」与「慢而全」的显式取舍。
3. **辣度/饮品温度/「清淡」无官方数据字段**：只能按名称避开 + 官方脂肪辅助排序 + 小字提示向门店核实，不宣称已验证。影响：极少数含隐性辣/冰的商品可能漏判。
4. **价格为短时效数据**（5 分钟 TTL + `checkedAt` 如实展示）：缓存过期后推荐阶段会重新核价（实测 +2~5s）。不冒充实时价。
5. **生产部署配置**：当前使用开发者本机 WorkBuddy 已授权模型（额度计入该账号），公开部署须配置部署方自己的 `MCFIT_LLM_BASE_URL/API_KEY`；生产环境已默认不读取个人本地配置。
6. **E2E 依赖本机 Chrome CDP**：跨环境复跑需安装 Chrome；单测与 verify-stage5 不受影响。

## 10. 当前页面是否真正适合普通用户——判断与依据

**判断：适合。**（但首次使用仍有 3–15s 等待，这是诚实边界，不是体验缺陷的掩饰。）

依据（全部为实际运行证据，非主观陈述）：
1. **核心验收场景 B 实测**：一句口语（含身体状态+三个口味偏好+预算）进来，0 次反问、0 张表单，直接得到 1 主推 + 2 备选；5 个需求标签全部是人话；主推是完整正餐而非最低价单品；价格是 MCP 实核价（含核价时点与 traceId）；未知项只有 4 行小字提示，无黄色警告框。
2. **E2E 19/19 通过**：其中 step 15 是专门针对「普通用户场景」的界面断言（标签、主推/备选数量、提示字号 11px、黄框 0、反问 0、预算意图、辣味分级）。
3. **六场景 31 条断言全过**：普通用餐没有被引导成营养考试；营养场景（C）也没有被削弱。
4. **移动端 390px 全流程可完成**，无横向溢出，详情为底部抽屉。
5. **技术信息不出现在普通用户视线**：帕累托/traceId/搜索量/营养编辑器全部折叠，高级入口保留可展开（成熟能力 14 项未丢）。
