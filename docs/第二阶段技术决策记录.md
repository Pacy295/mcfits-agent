# 技术决策记录（第二阶段）

记录「自然语言解析 → 多目标配餐 → 不可行解释」闭环中的关键判断、被否掉的方案，以及支撑它们的实测证据。
第一阶段的决策见 `技术决策记录.md`。

## 1. 运行时 LLM 到底能不能用（先验证，再动手）

**结论：可用，但不是"WorkBuddy 能理解自然语言"这件事本身。**

判断过程：

1. WorkBuddy 对话内能理解语言，只说明**宿主**有模型能力，不代表我们的独立 Node 服务有 API。
2. 检查 `本地开发者配置（不随仓库提供）`，发现两个 OpenAI 兼容端点配置：`mimo-v2.6-pro`（token-plan 网关）与 `qwen3.8-flash`。
3. 用最小请求实测：`mimo-v2.6-pro` → **HTTP 200，返回合法 JSON**；`qwen3.8-flash` → **HTTP 403 AccessDenied.Unpurchased**（未购买）。
4. 因此接入 `mimo-v2.6-pro`，走标准 `/chat/completions`，`response_format: json_object`。

**接入方式**：`src/llm/provider.js`

- 端点与密钥来源优先级：环境变量（`MCFIT_LLM_BASE_URL` / `MCFIT_LLM_API_KEY`）→ `本地开发者配置（不随仓库提供）`。
- 密钥只在服务端内存使用；`/api/llm/status` 只返回模型名与 baseUrl，不返回密钥（API 测试里有一条断言扫描响应体）。
- 多端点顺序降级：403/401 说明未授权，自动换下一个；全部失败才抛错。
- 运维开关 `MCFIT_LLM_DISABLE=1` 可强制关闭，用于验证"模型不可用时不伪造 AI 解析"（验收项 J）。

**踩到的坑**：探测请求最初给 `max_tokens=30`，推理型模型先把 token 花在思考上，`content` 为空 → 误判"不可用"。改成 256 后稳定。这条写进代码注释，避免以后又被当成"服务挂了"。

## 2. 解析层：模型只做语义，数值必须能被原文验证

模型输出的最大风险不是"看不懂"，而是"太懂事"——把「高蛋白」翻译成 `proteinMin=40`，把「练完胸」翻译成「需要 40g 蛋白」。三道闸门：

| 闸门 | 位置 | 作用 |
|---|---|---|
| 提示词铁律 | `llm-parser.js` SYSTEM_PROMPT | 明确列出"禁止推断阈值"的反例 |
| 数值反幻觉 | `schema.js normalizeConstraints` | 每个数值必须能在原文找到对应数字，否则置 null 并记 warning |
| 优化目标证据 | `schema.js OBJECTIVE_EVIDENCE` | protein/calories/price/taste 倾向必须有对应关键词，否则剔除并（必要时）回问用户 |

**为什么优化目标也要管**：`objectives` 会直接变成帕累托维度。模型擅自加一条 `protein=max`，就会让整个推荐偏向高蛋白，等于悄悄改了用户需求。所以它和数值字段一样需要证据。实测「练完胸想吃点东西」原本被模型加了 `protein=max`，现在会被剔除并生成一条待确认问题。

**硬/软清单完全由结构化字段派生**，不采信模型自己写的 `hardConstraints` 文案。原因：模型会把「预算 40」同时写成"预算 ≤ ¥40"和"总价不超过 40 元"，两份清单混在一起既重复又可能不一致。

**规则解析器不是摆设**：它是 LLM 不可用时的唯一降级路径，也是数值交叉校验的参照。为了让它可靠，踩过两个坑：

1. 「不超过 750 kcal」里的「超过」被当成下限关键词 → 用 `(?<!不)超过` 修正（`test/parse.test.js` 场景 B 是回归测试）。
2. 「最好来杯无糖可乐」被拆成 `["可乐","无糖"]` 两个词 → 改为组合成 `无糖可乐`。

**LLM 与规则冲突时**：保留模型值（语义更准），但记录 warning 并生成一条待确认项，让用户在前端表单里定。不静默覆盖。

## 3. 候选项：容器型商品是个真陷阱

第一版把 `rounds.length > 0` 一律当"套餐"，结果「派」「新地」「可乐」这类**选口味/选规格的容器商品**被当成一份正餐，出现了「¥8 的菠萝派」被推荐为"最便宜的方案"。

修正后的角色判定（`src/optimize/classify.js`）：

- 套餐角色 = 其组件的角色集合：有 `main` 组件才算 `main`，否则继承主要组件角色（drink / dessert / side）。
- 容器商品（角色不是 main）**不进入"正餐候选"**，而是作为一个"默认配置单品"进入对应角色的单品池；核价时带 `roundList`。
- 这样「可乐（默认 可乐小杯）」可以出现在 `主食+饮料` 组合里，但永远不会单独冒充一顿饭。

**候选空间**（有界，明示在 `searchScope.spaceNote`）：

- 套餐：每轮按"营养已知优先 + 补差价升序"取前 4 个选项 → 每套餐最多保留 6 个配置（含 2 个高蛋白配置）。
- 单品：`main` / `main+drink` / `main+side` / `main+side+drink` / `main+dessert` 五种形态，同一商品不重复出现。

**内容签名去重**：`componentCode×qty` 排序后做键，套餐与单品组合之间也会去重（同内容保留更便宜的形态）。

## 4. 价格：参考价只用于排序，最终一律重新核价

时间预算决定了不能对 2000+ 候选逐个 `calculate-price`。三层处理：

1. **参考价表**：套餐默认组合核一次价，变体按 `+ ΣdiffPrice` 推算；单品各核一次价。第一阶段的实测已证明「默认价 + diffPrice」与真实核价完全一致（¥34.00 / ¥36.00 / ¥36.00）。
2. **预筛留 5% 容差**：参考价可能略高，预算判断用 `est ≤ budget × 1.05`，宁可多核几个，也不误剪。
3. **最终核价**：落选候选逐一 `calculate-price`，用真实价复核全部硬约束；未核价的候选**绝不进入方案**（`checkHard` 的 `requirePrice` 分支）。

**一个真实踩坑**：单品组合里某个组件缺参考价时，最初用 `?? 0` 兜底，导致组合被当成"很便宜"通过预算，最终核价失败 13/30。修正为"任一组件缺价 → 整条参考价置 null"，这类候选会被计数到 `candidatesWithoutReferencePrice`，不静默丢弃也不瞎猜。

**为什么先按营养剪枝不会误剪预算可行解**：营养与价格无关，`checkHard(..., {nutritionOnly:true})` 明确跳过预算判断。这一步把需要核价的原子商品从 73 个压到 30~56 个，冷启动耗时从 9s 降到约 3s。

## 5. 帕累托：只在"用户真的在意"的维度上比

维度由约束推导（`buildDimensions`）：

| 维度 | 何时启用 |
|---|---|
| 价格（越低越好） | 永远启用——预算是硬约束，价格本身也是成本 |
| 蛋白质（越高越好） | 仅当用户说「想高蛋白」这类倾向时 |
| 热量（越低越好） | 仅当用户明确想降热量时；只给上限时不追最低 |
| 偏好命中（越多越好） | 存在可验证的偏好项时 |

**为什么「蛋白质 ≥ 30g」不进入维度**：那是阈值，达到即可。若把它当维度，会为了多 2g 蛋白淘汰便宜 5 元的方案，违背"不强制唯一最优"。

**退化维度的处理**（实测发现的问题）：用户提了「无糖可乐」但没有任何候选命中时，`prefScore` 恒为 0，这个维度会把帕累托退化成绩效"只看价格"。现在会先剔除"在可行解中无差异"的维度，再决定策略：

- 有效维度 ≥ 2 且非支配集 ≥ 2 → 帕累托 + 最远点采样，选 2–4 个。
- 否则 → 价格梯度：最便宜 / 每元蛋白质最高 / 蛋白质最高，再按"主商品必须不同"的原则补充差异化方案，差异度不足就少给，不硬凑。

**近重复处理**：内容重合度 > 66% 的候选只保留一个（更便宜的），避免"同款换个小食"占满推荐位。

## 6. 不可行：先给数字，再给话

`analyzeInfeasible` 全部是确定性计算：

1. **逐约束放宽**：每次只去掉一个硬约束，在**已核价**候选里重新判定，给出"剩几个可行 / 最便宜多少"。
2. **最接近的方案**：按归一化缺口（超预算比例 + 蛋白缺口比例 + 热量缺口比例 + 缺类别惩罚）排序，逐条列出"超预算 ¥X""蛋白质差 Y g"。注意：超预算额 = 核价 − 预算，是程序算出来的，不是文案里写的。
3. **搜索范围声明**：没覆盖全部候选时，明确写"不能断言全店不存在"。

**关键修正**：最初预筛后候选为 0 就什么都不核价，分析里只能写"已核价的 0 个候选"，等于没有证据。现在加了**诊断批次**：当预筛后候选不足 12 个时，额外挑"有参考价、缺口最小"的候选去真实核价（不进入推荐，只用于量化不可行程度）。这条是"不可行也要有证据"的底线。

## 7. 无法验证的限制（不吃辣/过敏/素食）

菜单与营养表都**没有辣度、配料、过敏原字段**。所以：

- 解析阶段标记 `verified: false`，并写明"菜单数据不含辣度/配料/过敏原字段"。
- 优化阶段不把它当可验证硬约束（不会因为「不吃辣」就声称筛掉了辣的）。
- 结果里通过 `dataQuality.unverifiableRestrictions` 明确列出，验收项 I2 断言"方案里不得出现声称已满足不吃辣"。
- 唯一能做的确定性处理：用户说「不要麦辣」时按商品名排除（这是可验证的）。

## 8. 性能

| 场景 | 耗时 | 说明 |
|---|---|---|
| 冷启动（无缓存） | ~3.0 s | 参考价 30–56 次 + 候选核价 40 次 + 套餐池构建 |
| 预热后（服务启动即预热 + 4 分钟续期） | 0.3–0.6 s | 参考价命中缓存；最终核价 40 次约 0.03–2 s |
| LLM 解析 | 1.5–4 s | 主要波动来源，与优化解耦 |

主要耗时环节依次是：LLM 解析 > MCP 候选核价 > 参考价表 > 候选生成（几十毫秒）。

MCP 并发从 8 提到 10（官方限流 600/min，仍有 40 倍余量），并给参考价表加了启动预热 + 4 分钟续期（价格 TTL 5 分钟），保证演示期间不会突然变慢。

## 9. 仍未解决 / 需要产品决策

1. **新品无营养 → 无法参与优化**：池子 117 个商品中 40 个（龙焰系列、枫糖厚松饼系列、心形薯饼等）因缺官方营养被排除。这不是算法能补的，只能等官方数据或人工确认。
2. **部分容器商品核价失败**（如「薄皮V翅双拼十翅」报 `60006 商品已售罄或不可售`）：这类商品目前被计入 `candidatesWithoutReferencePrice`，不会进入推荐；需要逐个确认售卖状态规则。
3. **protein 最高的方案可能不在被核价的样本里**：搜索是分层的（主食轮转 + 目标排序），不是穷举。`completeness` 已如实标注 `partial`。
4. **口味只能靠命中偏好词**，没有主观评分，也没有辣度/甜度这类属性。
5. **方案解释文案是模板生成的**（基于真实数值差距），未接入 LLM 润色——接入时需要再走一遍"不许编数字"的约束。

## 10. 审计修正：帕累托口径与预算算术（第二阶段补充）

### 10.1 缺陷：支配判定对"方案对象"静默失效

**现象**：验收报告列出 ¥31.5 / ¥38.5 / ¥35 / ¥33.5 四套方案，却声称"在价格这一唯一维度下两两互不支配"。价格单维时这是不可能成立的。

**根因**（三层叠加）：

1. `objectives.valueOf` 只读内部候选结构 `priced.priceFen`，而对外方案是 `price.fen`。取值得到 `null`。
2. `dominates` 遇到任一侧为 `null` 就直接 `return false`（"数据缺失不做判定"），于是**任何**两套方案都被判为"互不支配"。
3. 验收脚本恰好拿方案对象去调 `dominates`，因此断言永远通过——**空断言**。

**为什么之前没暴露**：引擎内部用候选对象计算帕累托是对的，错的是"对外口径"和"验收取数"。测试断言的对象形态与判定函数期望的形态不一致，等于没测。

**修复**：

- 新增 `src/optimize/shape.js` 作为唯一取值入口（`priceFenOf` / `nutritionOf` / `snapshotOf` / `deltaOf`），同时支持两种结构。
- `objectives.valueOf` 改为走 shape；`dominates` 增加 `comparable > 0` 保护（维度为空时不产生支配关系）。
- `compare.js`、`infeasible.js`、引擎组装全部改用 shape，杜绝各模块各算一套。

### 10.2 缺陷：把"差异化补充"混在帕累托结论里

原来 `selection.note` 在 `front.length >= 2` 时统一写"筛出 N 个非支配解"，即使实际走的是价格梯度补充。用户看到的四套方案里有三套其实被最低价方案支配，但文案没有区分。

**修复**：方案级新增 `pareto` 字段，选择结果新增 `basis` 与计数：

```jsonc
plans[].pareto = {
  nonDominated: false,
  label: "差异化补充",              // 或 "严格非支配"
  dimensions: ["priceFen"],
  dominatedBy: [{ name, priceFen, deltaFen }],  // 真实支配者与差价
  note: "..."
}
selection = {
  basis: "strict-front" | "ladder",
  strictParetoSize, strictParetoCheapestFen, strictParetoSample,
  nonDominatedSelected, diversifiedSelected, dimensions, note
}
```

**口径规则**：

- 严格帕累托前沿 **只在整个已核价可行解集合上计算**，与"推荐了哪几套"无关。
- 价格单维时，前沿 = 最低价那一批；其余方案一律标 `差异化补充`，并给出"比谁贵多少"。
- 只有 `strict-front` 策略下，返回的方案才全部是严格非支配解。
- 价格梯度策略下，**严格前沿成员优先入选**（最多占一半名额），绝不用更贵的差异化方案把它挤掉；剩余名额才给每元蛋白最高/蛋白最高/差异明显的补充方案。
- 产品原则不变：仍然给多套方案，但**严格非支配**与**为丰富选择补充的方案**必须能一眼分开。

### 10.3 缺陷：报告数字与实际入参不一致

**现象**：汇报写"预算 ¥15，最低替代 ¥48，超预算 ¥36"。48−15=33，不是 36；而脚本实际传的是 `budgetMax: 12`（48−12=36）。程序算得对，是**说明文字里的输入写错了**，两者对不上。

**修复**：

- 验收脚本把入参显式定义成常量 `INF_BUDGET_YUAN = 12`，并在控制台打印真实入参，报告随输出一起存档。
- 新增 E5 检查：对每条近似方案断言 `excessFen === priceFen − budget*100`，且文案里的金额字符串与该算术值一致（不只检查"文本非空"）。
- 单测 `test/pareto.test.js` 里用 `budgetMax: 10` 再验一遍同样的算术关系，避免只对一个数字碰巧成立。

### 10.4 缺陷：三处数值各取一遍

方案、对比、不可行分析原本各自从候选对象里取价格/营养，字段名还不完全一样（`priced.priceFen` vs `price.fen` vs `candidate.priceFen`）。这类重复取值迟早会漂移。

**修复**：统一走 `shape.js`；对比返回 `provenance`（两条方案的 traceId / checkedAt / priceFen），验收项 `CONSIST` 断言：

- 对比价差 = 两方案价差（分，整数）
- 对比里的热量/蛋白/价格/traceId 与方案字段逐一相等
- 不可行近似方案的数值齐全、且与违规项自洽（E5）
