## 1. budgetMax 冲突的真实根因

**根因：规则解析器把区间起点当成了上限。**

「预算35到45块」中，规则解析器的预算正则先命中第一个数字 35，将其作为 `budgetMax`；而 LLM 正确抽出上限 45。两路结果（35 vs 45）进入交叉校验，触发 `num_conflict_budgetMax` 冲突警告，并在页面上暴露技术字段。

即：冲突不是模型错了，而是规则正则只支持单值预算、不识别区间，把「35到45」的起点 35 误当最高预算。修复过程中未删除交叉校验，而是让两路解析都先识别完整区间。

## 2. 预算区间解析修复后的具体结果

修复落点（3 处解析路径共用 `parseBudgetRange`，src/parse/intent.js）：

- `rule-parser.js` / `schema.js` / `llm-parser.js` 均先识别完整数字区间，再取单值预算；
- `normalizeConstraints` 区间归一：下限=起点、上限=终点；
- 交叉校验语义等价静默统一（llm-parser.js：一方给起点、一方给终点 → 统一为区间，不算冲突，不删校验）；
- 真冲突时 `conflictQuestion` 输出自然语言（例：「我暂时按45元以内理解，你可以修改预算。」），前端 `humanizeWarnings` 过滤 budgetMax 等内部字段。

`verify-budget-range.mjs` **20/20 通过**，覆盖：

| 输入 | 结果 |
|---|---|
| 预算35到45块 / 35～45元 / 35-45块 / 35至45元 / 三十五到四十五元 | 全部 → 区间 35–45、上限 45、intent=range，五种写法一致 |
| 最多45元 | → 硬上限，budgetMin=null |
| 45元左右 | → 软目标 target |
| 越便宜越好，45元以内 | → minimize |

以上每个场景均核对模型解析、规则解析、最终结构化输出三路（含真实 LLM 端到端）。语义一致时 warnings 为空、不显示冲突警告；区间起点 35 不再被当成上限。

## 4. 原因定性

**属于营业时间原因（有证据），不是门店永久关闭。**

判定依据：5 家门店 `businessStatus:false` + 营业时间 07:00–00:00（3350241）等，当前 01:06 处于全部门店打烊时段（跨零点判定已单测覆盖）。分类产物为 `category: outside_business_hours`，文案「这家门店的营业时间是 07:00–00:00，现在还没开门（或已打烊）。」

**未硬编码 600057=关闭**：分类函数 `classifyMenuFailure` 只在营业时间证据成立时给出 outside_business_hours；同码不同证据 → 不同结论（回归 MCP④ 覆盖），无证据时只说「暂时查不到原因」。

## 7. 「不太饿、凉凉的、冷饮、35–45元」的真实解析输出

2026-10-25 01:51 对 5211 服务 `POST /api/parse` 实测（真实 LLM，source=llm，degraded=false，reasoning_tokens=0）：

```json
{
  "budgetMin": 35, "budgetMax": 45, "budgetIntent": "range",
  "preferences": { "avoidOily": true, "avoidIce": null },
  "preferredFoods": ["冷饮"], "preferredCategories": ["drink"],
  "warnings": [],
  "notes": "用户提到不太饿、想吃凉的、别太油腻，作为软偏好背景；冷饮为软偏好非硬需求。"
}
```

- 区间 35–45、上限 45，**无冲突警告**（budgetMax 不再出现 35 vs 45 冲突）；
- 「今晚不太饿」→ lightMeal 小份优先（不为凑 45 加餐、不虚构热量上限）；
- 「凉凉的」（preferCoolFood，食物温度）与「最好能有杯冷饮」（preferColdDrink，饮品软偏好）**分开处理**；菜单无温度数据不声称「××是凉的」，冷饮仅按名称/规格证据辅助；
- 「别太油腻」→ 脂肪数据仅辅助排序，不等同「清淡」，保留不确定性说明；
- 优先级：硬约束 → 不太饿场景 → 低油腻/冷饮偏好 → 35–45 价位；输出 1 主推 + ≤2 备选（取舍不同）；低于 35 不惩罚且明说「不硬凑、不为凑满预算加餐」。
